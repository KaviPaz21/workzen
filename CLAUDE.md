# WorkZen

AI-assisted workspace for company departments, built department by department. First module: RecruiteOne (HR applicant tracking). See README.md for run commands.

## Layout

- `BE/` back end (FastAPI), `USERFE/` front end (React + Vite + TypeScript). These two names are fixed. `COWORKER/` is a separate small Python helper that runs on a user's own computer for the AI Assistant's Co-worker (see General tools).
- Back end layers: `api/` → `services/` → `repositories/` → `integrations/`, with `schemas/` and `agents/`. Each layer holds a subpackage per module (`recruiteone/`), so a new department is additive.
- Front end is one web app with a persistent sidebar: Home, Departments (each expands to its tools), General tools. A tool's own functions appear as a top tab bar inside the tool (`layouts/ToolLayout.tsx`), not in the sidebar.
- `src/modules/registry.ts` is the single source for the sidebar, home page, breadcrumbs and "coming soon" pages. To add a department, tool or general tool, add an entry there. Planned entries link to `/soon/:id`.
- Tool URLs follow `/<department>/<tool>/<function>`, for example `/hr/recruiteone/jds`.
- `src/modules/<tool>/` holds pages, components, data and types for one tool. Shared pieces live in `src/components/ui` and `src/components/layout`.

## Stack decisions

- LangGraph is the core agent framework. Chat model and evaluators come from Azure AI Foundry (model deployment name is set in `.env`).
- Azure Cosmos DB is the main database, Azure Blob Storage stores files.

## General tools

- AI Assistant (`/assistant`, first live general tool, registry entry `assistant`): an internal chat bot. Front end in `src/modules/assistant/` (page, `useAssistant` hook, components, `services/assistantApi.ts`, styles in `styles/assistant.css`); it is the one place that uses a Calibri / sans-serif font stack instead of Inter and Source Serif 4, by request. Layout: a hamburger button in the tool's own bar opens the previous-chats panel (New chat, chats grouped Today / Yesterday / Previous 7 days / Older, delete with confirmation); next to it a GPT | Internal KB toggle, drawn as a capsule (white fully rounded track with a black pill that slides to the selected option, small icons; the canvas Preview | Code switch uses the same capsule style). An empty chat shows a greeting by hour in Asia/Kolkata (UTC+5:30) with the input centered; after the first prompt the input docks at the bottom. The look follows a Gemini-style reference but stays grayscale: a very pale page (#f9f9fb) with a wide soft gray glow behind the centered input (fades out once the chat has messages), a light-weight greeting, and a white pill-shaped input (32px radius, soft shadow) that holds everything on one row: placeholder attach and image icons (no upload yet) on the left, the text area, then borderless model and effort dropdowns and a round send button on the right. It wraps to two rows on narrow widths and grows into a taller pill for multi-line text. The New chat button and the chat rows use the same capsule language (white capsules; the open chat is a black capsule). A round "scroll to the latest message" button floats above the input whenever the chat is scrolled more than about 240px from the bottom and smooth-scrolls back down when clicked. A rail on the right has one mark per user question (hover shows the question, click jumps to it, the current one follows scrolling); the marks are right-anchored capsules that grow to the left by distance from the current question (26px current, 18px, 12px, then 8px dots), so the ones above and below it are graded too. Answers stream and render as markdown (`react-markdown`).
- AI Assistant canvas: code blocks in answers show Copy and, for html (and svg), javascript and python blocks, a Preview or Run button that opens a canvas panel beside the chat (`components/CanvasPanel.tsx`, `lib/canvas.ts`, `lib/pythonSandbox.ts`, `state/usePythonRunner.ts`). Everything runs in the user's browser, never on the server. HTML and JavaScript run in an iframe with `sandbox="allow-scripts allow-forms allow-modals"` and no `allow-same-origin`, with a bridge that sends `console.*` calls and errors to a Console panel. Python runs with Pyodide (loaded from the jsDelivr CDN, so it needs internet) in a Web Worker inside a hidden sandboxed iframe, so it has an opaque origin and cannot read the WorkZen API or the page; each run gets fresh globals, numpy, pandas and matplotlib load on demand (plots come back as images), runs are stopped after 20 seconds or with Stop, and `input()` and file access are unavailable. The canvas has an editable code view, Run or Refresh, Copy, a wide toggle and Close; the system prompt in `agents/assistant/prompts.py` tells the model to answer with runnable ```html, ```python or ```javascript blocks. Canvas edits are not saved with the chat.
- Co-worker (AI Assistant): a switch at the bottom of the chats panel (`CoworkerSwitch` in `SessionsPanel`) lets the assistant do small tasks on the user's computer. Because a web page cannot control a PC, it works through the local app in `COWORKER/` (FastAPI on `127.0.0.1:8765`, own `.env` and venv, same Python rules). Customers are non-technical, so setup has no commands or codes: the setup dialog offers `Download for Windows` (`coworker_download_url` from `GET /assistant/options`, backed by `COWORKER_DOWNLOAD_URL` or `COWORKER_INSTALLER_PATH` served at `/assistant/coworker/installer`), then polls `/ping` and, once the app is found, shows one `Connect` button that calls `POST /pair`, which makes the app show a native Windows Yes/No question (default No) and only then returns the token (kept in localStorage; `POST /unpair` replaces it). The app is a single `WorkZenCoworker.exe` built by `COWORKER/build.ps1` (PyInstaller, bundles the build-time `COWORKER/.env` so the allowed web origin is set by the administrator, never hardcoded): first run asks to install (copies itself to `%LOCALAPPDATA%\WorkZen Co-worker`, adds a start-with-Windows entry and a Start-menu shortcut, starts), then runs in the background with a tray icon (open folder, start with Windows, disconnect, uninstall, quit); a crash writes `last-error.log` and shows a plain message. The exe is unsigned by default, which makes browsers and SmartScreen say "not commonly downloaded" (the setup dialog explains the two clicks); `build.ps1` signs it when `COWORKER_SIGN_PFX` + `COWORKER_SIGN_PASSWORD` + `COWORKER_SIGN_TIMESTAMP` or `COWORKER_SIGN_COMMAND` are set, and IT can deploy it per user with `--install` / `--uninstall` (silent). Details in README.md. `--serve` runs it in a terminal for development and tests, and `COWORKER_PAIRING_PROMPT=false` skips the native question for automated tests only. It accepts only allowed browser origins (and the Private Network Access preflight), and offers a fixed action list: `open_in_default_browser`, `open_file`, `create_word_document` (python-docx), `create_excel_document` (openpyxl; sheets of columns and rows, text cells never turn into formulas; the model uses it to write a test case document after testing and returns the path) / `write_text_file` / `read_text_file` / `list_files` (all confined to one workspace folder, flat names, never overwriting), and the browser tools `browser_open` / `browser_read` / `browser_inspect` (lists tags, types, labels, ids and `e12`-style references of inputs, buttons and links) / `browser_click` / `browser_hover` / `browser_type` / `browser_select` / `browser_press` / `browser_scroll` / `browser_wait` / `browser_expect` (pass/fail checks for testing an app) / `browser_issues` (console, script and HTTP errors) / `browser_close` (Playwright driving the installed Chrome or Edge, http and https only; the page gets a visible black-and-white Co-worker mouse pointer with a name tag that glides to each target, a click ripple and a highlight box, injected by `actions/page_scripts.py`; it is Playwright's own virtual mouse, so it never moves the user's real one). No shell, no deletes. The assistant side is a second LangGraph graph (`agents/assistant/coworker_graph.py`, tools in `coworker_tools.py`, model from `get_coworker_model` which uses the Responses API because this deployment rejects function tools together with `reasoning_effort` on chat completions). Flow: `POST /chat` with `coworker: true` streams events; each tool call becomes an `action` event (arguments validated first); the UI decides by the user's permission mode (`lib/permissions.ts`, kept in localStorage, picked in the bar next to the Co-worker chip or in the settings dialog) whether to run it at once or show an Allow / Deny card, and runs it against the helper from the browser, and posts the result to `POST /assistant/coworker/runs/{run_id}/actions/{action_id}` while the server-side run waits (180 s) on it; denials, failures and timeouts go back to the model. Runs live in memory (`CoworkerRuns`), so they need a single back end process. Permissions: every action carries a risk from the back end (`risk_of` in `coworker_tools.py`): low (everything inside the Co-worker browser: reading, inspecting, navigating, clicking, typing, choosing, scrolling, checking), medium (opening a file or the default browser on the user's computer) or high (creating a file or document, including `create_excel_document`, or clicking something that creates or submits). Modes: Ask me for every action, Ask only for important actions (the default; auto-runs low, asks for medium and high) and Allow everything except creating (auto-runs low and medium). Whatever the mode, high always asks, and Co-worker can never delete: delete requests (model-declared `effect: deletes`, or delete/remove/erase words in the target or `label`) are refused by the back end without asking, and the helper (`actions/safety.py`) refuses to click anything labelled that way. The helper also describes the real element (and the one under the pointer) before each click: a create or submit element, or Enter inside a non-search form, returns `needs_approval` (except chat boxes: a lone textarea or message-like input, and its Send button, count as chatting, so testing a chatbot never asks per message) unless the UI passed `allow_create` (only after the user pressed Allow on a card for a high action or on the follow-up confirmation card); it never types into password fields and dismisses page dialogs. Browser element tools take a plain-words `label` for the user-facing summary. Chat widgets work: `browser_wait` with `settle` waits until the page stops changing (a bot still writing), and page text longer than the limit keeps its start and its end, because the newest messages are at the end. Up to 30 tool calls per task. The app reports its `version` on `/ping` and its `actions` on `/status`; `GET /assistant/options` lists the `coworker_actions` the back end needs, and when the installed app lacks one the UI shows an out-of-date notice with the download (and fails that step with a plain "update the app" message instead of "Unknown action"). Opening a newer `WorkZenCoworker.exe` while an older copy runs asks "Update now?", stops the old copy (the process listening on the port, after `/ping` confirms it is Co-worker), replaces the installed file and starts the new one; `--install` does the same silently. Bump `APP_VERSION` in `COWORKER/app/main.py` and `version_info.txt` with every release. Web page text returned to the model is marked untrusted and the prompt forbids following it or typing secrets. Saved assistant messages keep an `actions` trace shown as Co-worker actions. The helper is delivered as a no-code installer exe (`COWORKER/build.ps1`, PyInstaller, with a version-info resource): the setup dialog offers the download (served by `GET /assistant/coworker/installer` from `COWORKER_INSTALLER_PATH`, or `COWORKER_DOWNLOAD_URL`), detects the running app by itself and Connect shows a native Windows Allow dialog (no codes or commands for users). The exe is unsigned by default, which triggers the browser / SmartScreen "not commonly downloaded" warning (explained in the setup dialog); `build.ps1` signs it when `COWORKER_SIGN_PFX` + `COWORKER_SIGN_PASSWORD` + `COWORKER_SIGN_TIMESTAMP` or `COWORKER_SIGN_COMMAND` are set, and IT can deploy it per user with `--install` / `--uninstall` (silent). Details in README.md.
- AI Assistant back end (`/api/v1/assistant`): `GET /options` (models, efforts, mode status), `GET /sessions`, `GET|DELETE /sessions/{id}`, `POST /chat` (NDJSON stream of start, delta, done or error events). Sessions are private to the `X-User-Id` header (the demo "view as" user, UI-trusted like the rest) and stored in the Cosmos records container under collection `assistant_sessions` (`repositories/chat_session_repository.py`). The agent is a LangGraph graph (`agents/assistant/graph.py`): GPT mode goes straight to the model; Internal KB mode first retrieves (BM25 over chunked documents from the Blob container `AZURE_STORAGE_CONTAINER_KB`, default `knowledge`, in `services/assistant/knowledge_service.py`, re-read at most once a minute; .pdf .docx .txt .md), answers only from the numbered excerpts with citations, and replies with a fixed "not found" message without calling the model when nothing matches. Documents are added to the knowledge container directly (no upload screen yet). `ASSISTANT_MODELS` is a comma-separated list of Foundry deployment names for the model picker (defaults to `FOUNDRY_CHAT_DEPLOYMENT`); the effort picker sends `reasoning_effort` (low, medium, high).

## Back end rules

- No comments or docstrings in Python code.
- Use plain, descriptive function names. Never start a function name with an underscore.
- Never hardcode keys, secrets or endpoints. Everything goes in `.env` and is read through `app/core/config.py`. Keep `.env.example` in sync.

## Front end rules

- UI must look professional, clear and easy to navigate.
- Theme is strictly black and white (grays only). No purple, yellow or other accent colors. Status is shown with fill, outline and weight (filled black = positive, outline = negative, gray = neutral), not hue.
- Dense and professional: 8px outer margin, 12px gaps, 8-12px corner radius, 14px base text, 13px tables. Do not add generous padding or large rounded shapes.
- Source Serif 4 for page titles, card titles and big numbers, Inter for everything else.
- Layout (RevenueX template): a flush frosted sidebar on a light gray gloss background, and one white content panel that scrolls on its own. The panel starts with a flat top bar that stays pinned: tool sub-navigation (Dashboard, JDs, Vacancies...) on the left, notifications, settings and account on the right. A small breadcrumb line sits above the page title. The sidebar holds navigation only.
- Design tokens live in `src/styles/tokens.css`. Reuse them instead of new colors. The `accent-*`, `green-*`, `amber-*` and `coral-*` token names are kept for compatibility but map to grays.
- All RecruiteOne data lives in Azure Cosmos DB, with CV files in Azure Blob Storage. The back end exposes generic record endpoints (`GET /api/v1/recruiteone/records`, `PUT|DELETE /records/{collection}/{id}`, collections: jds, vacancies, candidates, batches, interviews, scorecards, interview_scores, approvals, stored in the Cosmos container `COSMOS_CONTAINER_RECORDS` partitioned by `/collection`), CV file endpoints (`PUT|GET /files/{candidate_id}`), stored-CV scoring (`POST /scoring/candidates/{candidate_id}`) and public application endpoints (`/public/vacancies/{token}`, `/public/vacancies/{token}/applications`).
- `modules/recruiteone/state/RecruiteOneStore.tsx` loads everything from `/records` on start, applies changes in memory at once, writes each changed record back (in order) and re-reads every 10 seconds and when the tab becomes visible, so several people share the same data. Vacancy counts are derived from candidates, never stored. There is no sample data and no localStorage copy of business data. The `/apply/:token` page does not use the store.
- Approvals (RecruiteOne tab right after Dashboard, `pages/ApprovalsPage.tsx`, components in `components/approval/`, logic in `services/approvalMath.ts`, step definitions in `data/approvals.ts`): a hiring request (position name, recruiter name, level, department, JD details, why it is required, value of the position) is saved as a draft or submitted, then passes four steps in order: department head (chosen from the department's people when creating), Finance, HR, final Management (any person of that department can decide; the head step is for the chosen person only; UI-enforced like interviews). A rejection at any step rejects the request; rejecting needs a comment. Status stored: draft, pending, approved, rejected. "Finished" is derived (approved and a linked vacancy is closed), like JD status. Filters: All, Drafts, Pending, Approved, Rejected, Finished. A JD may optionally carry an `approval_id` (pending or approved requests; set in the New JD wizard or the JD popup Approval tab). A vacancy must carry an `approval_id` of an approved request that no other vacancy uses (preselected from the JD's approval); its department comes from the approval. Closing a vacancy (Close vacancy in the vacancy popup, reversible with Reopen) finishes its approval. The approval can be opened from the JD popup, the vacancy popup (Approval tab), the CV Pool vacancy and batch headers and the interview header (`ApprovalLink`). The demo people directory includes Finance and Management people so every step has approvers.
- Vacancy popup flow: name, then a searchable pick of non-deleted JDs, then a required pick of an approved hiring request, then two independent optional choices: Shareable link (closing date required, generates `/apply/<token>`) and Schedule pipeline (name, description, stages with max candidates and interviewers; HR people are the default interviewers). Saving leads to an "Upload CVs now" action. From a JD the same popup opens with the JD preselected and an extra tab listing that JD's vacancies. `/apply/:token` is the public application page (JD details, application form, CV upload).
- CV batches: Upload CVs asks for a vacancy, a batch name, files and/or applications fetched from the shared link (link applications wait unbatched until fetched). Each CV in a batch is scored by the back end (`POST /api/v1/recruiteone/scoring/cv`, multipart file + JD) with 8 benchmark scores and reasoning; the overall score is the weighted average using the JD weights, ignoring benchmarks the JD does not list. Scoring is grade-point based (ported from cv-analyzer-recruitone): the model (seed from a hash of CV + JD, results cached; no temperature is sent because the Foundry deployment only accepts its default) only returns evidence, never scores: a matched/not-matched flag per listed JD item, alternatives with a 0-100 relevance (technical skills, certifications, education; extra-curricular wins always count as full), and required vs available months for experience. `agents/recruiteone/grade_points.py` turns that into a 0-4 grade point (required item = 2.5 credits at grade 4 or 0; alternative = 2 credits at relevance/100 x 4; experience below the requirement = 0.5 + coverage x 3.5), and score = grade point x 25. The vacancy popup CVs tab drills batches > sorted CV list > per-benchmark reasoning. CV files are kept in Blob Storage (`lib/cvFiles.ts`), so they can be viewed and rescored from the server. Excel export (top N, `services/exportExcel.ts`) loads exceljs lazily.
- The Dashboard cross-filters like a Power BI report: selecting a vacancy in "Open vacancies in progress" (click again, or Clear filter, to deselect) filters the KPI cards (the first becomes the vacancy's status), Evaluation outcomes, Recent evaluations and Recent activity to that vacancy, without navigating; the table keeps listing all open vacancies so the selection can be switched. "All vacancies" and each row's arrow button still go to the Vacancies tab.
- Tabs of RecruiteOne: Dashboard, Approvals, JDs, Vacancies, CV Pool, Interviews. There is no Evaluate tab: scoring happens when CVs enter a batch, and re-evaluation is done from the CV Pool.
- CV collection state is derived (`collectionState` in `data/stage.ts`): Closed (HR pressed Close collection), Ended (the closing date has passed, so the shared link no longer accepts applications, but HR has not closed the collection yet) or Collecting. The CV Pool badges and its Collecting / Collection over filters, the vacancy popup, and the interview screens all use it. Ended does not lock uploads or the pipeline; only Close collection does.
- CV Pool drills vacancies > batches > CVs (state in URL params `vacancy` and `batch`). Ticking CVs marks them selected for interview. Selected CVs are never re-evaluated and are listed separately with the role and pipeline details. "Close collection" needs a pipeline and at least one selected CV, locks uploads, the pipeline and the shared link, and creates an Interview.
- An Interview record (id `int-<vacancy id>`) is created as soon as a vacancy has a pipeline (the store backfills it for existing pipelines), with no candidates. Scored CVs enter stage 1 at any time, before or after the collection closes, through `SendToPipelineModal`: "Proceed with pipeline" on the vacancy popup's CVs tab (defaults to top scored) and "Send to pipeline" in the CV Pool vacancy and batch headers (defaults to the ticked CVs). It offers the top scored CVs ranked together across all batches (editable number, starting at stage 1's max candidates, with a preview of who goes), the ticked CVs, or all scored CVs not yet in the pipeline, with a non-blocking warning above stage 1's free places. The vacancy popup's first KPI box shows the vacancy status (not openings). Sending marks them selected, and CVs in the pipeline can no longer be un-selected or re-evaluated. "Close collection" adds the remaining selected CVs and keeps everyone's progress. In the interview Overview, HR ticks pending candidates (or "Select all pending") and passes them to the next stage or rejects them in bulk, limited to the places left in the next stage (or the vacancy openings for the last stage), with a confirmation. The Interview record also lets scorecards be prepared earlier. The Interviews tab lists every vacancy with a pipeline: closing date, interview dates (range and stage count), CV collection open or the interview progress, and the user's part. Its page opens on a "Job & CVs" view while the collection is open: key dates, the JD (requirements and original text) and the scored CVs (best first, with View CV); after closing it lists the interview's candidates (interviewers only those who reached their stages). Interviewers can create their own scorecards at any time; scoring opens once candidates exist. Only HR people can create or edit the common (stage-wide) scorecard; this is enforced in the store (`saveScorecard`) as well as hidden in the UI.
- Pipeline stages have a schedule date. Interviews live under the Interviews tab. HR users (department Human Resources) see every interview and every interviewer's scorecard and scores, combine them (average of each interviewer's percentage) and pass or reject candidates stage by stage. An interviewer assigned to a stage sees only that interview and stage, defines their own scorecard (criteria and highest score) and scores candidates beside the CV; nobody else's scorecards or scores are shown to them. This is enforced in the UI only until real sign-in exists. The top-right user menu is a demo "view as" switch (`state/CurrentUser.tsx`).
- Pages with a main table (JDs, Vacancies, CV Pool) use `PageLayout fill`: the page never scrolls, only the table body does, with a sticky header. Popups blur everything behind them, and every popup (wizards, tabs, confirmations, viewers) has the same fixed width and height (960x680, shrinking only to fit the screen). Content scrolls inside the popup; never size a popup to its content.
- Status badges never use a black fill, so they cannot be mistaken for buttons.
- A JD has 8 requirement buckets (technical skills, soft skills, experience, responsibilities, education, certifications, job requirements, extra-curricular) and a 0-100 weight per bucket, default 50. JD status is derived: Published = has an open or on-hold vacancy, Draft = never had a vacancy, Deleted = soft deleted.
- Field names mirror the API (snake_case). The only static data left is the demo people directory (`src/modules/recruiteone/data/people.ts`) used for the "view as" user switch and interviewer pickers, plus bucket and level definitions.
- Interview page: stage tabs mark the Current stage (furthest stage with active candidates) and Done stages; the right-side nav is Overview | Create scorecard | Score candidates | Results. HR sees Overview (all candidates, per-interviewer %, View CV, pass/reject), Create scorecard (common scorecard for the stage, plus a personal one if HR is assigned), Score candidates (also for HR; a scorer who is not an assigned interviewer is added to that stage's score columns) and Results (HR only: ranking, per-interviewer scores, previous-stage score, selection by top N or manual ticks, optional reject-the-rest, limited to the places left in the next stage or the vacancy openings). Assigned interviewers see only Create scorecard (their own; the common one read-only) and Score candidates (candidates left, CV in the middle, scorecard right; the panes are resizable via `components/ui/ResizableColumns.tsx` and widths persist; a Full screen button in the toolbar above the panes expands the whole workspace over the app and asks the browser for real fullscreen too, and Esc or Exit full screen returns). An interviewer scores with their own scorecard if they have one, otherwise the common one. Interview components live in `modules/recruiteone/components/interview/` and shared math in `services/interviewMath.ts`.
